## Changes
- Douyin short links now have the yt-dlp fallback: a `v.douyin.com` short link, or the whole sentence the Douyin app copies on Share, is followed once to find the video id. When f2 cannot read the video, yt-dlp gets the full `douyin.com/video/<id>` link (it has no extractor for the short form), so the download no longer ends at "Add a video file" for that reason alone. A link that already carries its id (`/video/`, `?modal_id=`, `iesdouyin.com/share/video/…`) needs no network look-up for this (#51).
- A stalled network no longer holds the first Douyin download for about three minutes. f2 loads in a background thread and Motio waits at most 15 s for it (it was about 135 s when the traffic to Douyin's token server is silently dropped); the load keeps going, and if it gets through, the next download uses f2 at once. A failed or timed-out load is not started again for two minutes, as before (#51).
- With no connection to Douyin the error now says so: "Could not connect to Douyin. Check your internet connection (or VPN, proxy, DNS filter), then try again" (in Vietnamese when the app is). Before, yt-dlp's "Douyin asks for fresh browser cookies" hint was shown, because yt-dlp gives it even with no network. Only that hint is replaced; any other yt-dlp error (a 403, a removed video) is shown as it is, and the cookie hint stays when f2 did reach Douyin. A short link or a user page that cannot be fetched for lack of a connection stops with the same message, since yt-dlp could do nothing with it (#51).
- Smaller: a Douyin link that carries its id keeps its yt-dlp fallback even when the HTTP client cannot be built (a broken `SSL_CERT_FILE`, a SOCKS proxy without its package); an f2 load that stops without a result, for instance f2 exiting on a broken config file, is reported as a failure and not as a network timeout; a download whose every CDN link fails on the network says it could not connect (#51).

## Verification
- GitHub CI passed on #51 (engine tests on Ubuntu and Windows, desktop app build and clippy) and on the release pull request.
- Automated tests: TESTS_FF passed locally on Linux with FFmpeg on the release code; TESTS_NOFF with FFmpeg and ffprobe hidden, as on the CI runners. The new tests cover the short-link look-up and fallback, the f2 loader (a stalled load given up on, a late success used by the next download, one load at a time, a load that exits), the network-error classification (f2's own error names, errors wrapped by other errors) and the message that replaces the cookie hint.
- With the real f2 and a local port that drops connection attempts (as a network that swallows packets does), the first load gives up at 15.0 s and the next two calls fail at once; before this change that wait was about 135 s. With the real f2 and yt-dlp behind a proxy that refuses every connection, a full link, a short link and the full link again all say "Could not connect to Douyin" within 3 s, and a YouTube link keeps its own error.
- Review before release: three independent reviewers (the f2 loader and its threads, the control flow of the download, the documents and tests) went through the change and their findings were challenged by skeptics; eight real defects were fixed in #51 before it was merged, each with a test that fails when the fix is taken out. The release notes were then fact-checked against the code the same way.
- Not tried yet: a real Douyin run of this change (the build environment cannot reach Douyin; the f2 download itself was tried on the Mac for 0.7.13), the 15 s wait against a real stalled connection on a user's network, Douyin through f2 on Windows and from the Hetzner server, a real HeyGen clip and real fal pictures and clips, and the in-app update from 0.7.13 to 0.7.14. Known limits: after a failed f2 load a download within the next two minutes still skips f2, even if the connection is back; yt-dlp can add up to 30 s before an error shows, and so can following a short link; a DNS filter that answers `0.0.0.0` for a short link still shows yt-dlp's own error.
- The tag also carries two repository chores (#48, #50: a log hook for cloud sessions under `.claude/`) that the app and the engine do not use. #40 (TikTok inbox) is not in this release.

## Downloads
- macOS Apple Silicon: DMG installer.
- Windows x64: EXE or MSI installer.
- In-app updates use the signed update bundles and latest.json included in this release. The update replaces the engine inside the app only: a remote engine (the Hetzner server, or the Windows PC) has to be updated on its own, by a deploy or by reinstalling its MSI. Until it is, that engine keeps the 0.7.13 behaviour for Douyin (a first failure after about three minutes on a stalled network, and the cookie hint when there is no connection). Settings → Engine status shows 0.7.14 once the engine is updated.
