## Changes
- Douyin short links now have the yt-dlp fallback: a `v.douyin.com` short link, or the whole sentence the Douyin app copies on Share, is followed once to find the video id. When f2 cannot read the video, yt-dlp gets the full `douyin.com/video/<id>` link (it has no extractor for the short form), so the download no longer ends at "Add a video file" for that reason alone. A link that already carries its id (`/video/`, `?modal_id=`, `iesdouyin.com/share/video/…`) needs no network look-up for this (#51).
- A stalled network no longer holds the first Douyin download for over two minutes. f2 loads in a background thread and Motio waits at most 15 s for it; when the traffic to Douyin's token server is silently dropped, f2 retried for about 135 s (the packaged 0.7.13 engine took 138 s to fail). The load keeps going, and if it gets through, the next download uses f2 at once. A load that failed is not started again for two minutes, as before, and a slow one that is still running is never started a second time (#51).
- With no connection to Douyin the error now says so: "Could not connect to Douyin. Check your internet connection (or VPN, proxy, DNS filter), then try again" (in Vietnamese when the app is). Before, the hint "Douyin asks for fresh browser cookies" was shown, because yt-dlp fails with its "fresh cookies are needed" error even when there is no network. Only that hint is replaced, and only when f2 could not get through to Douyin or to its video servers; any other yt-dlp error (a 403, a removed video) is shown as it is, and the cookie hint stays when Douyin did answer. A short link or a user page that cannot be fetched for lack of a connection stops with the same message, since yt-dlp could do nothing with it (#51).
- Smaller: an f2 load that stops without a result, for instance f2 exiting on a broken config file, is reported as a failure and not as a network timeout; when every video-server link fails on the network the download goes on to yt-dlp, and if yt-dlp then gives its cookie hint the error says it could not connect, like the other no-connection cases (#51).

## Verification
- GitHub CI passed on #51 (engine tests on Ubuntu and Windows, desktop app build and clippy), on master after its merge, and on the release pull request.
- Automated tests: 593 passed locally on Linux with FFmpeg on the release code; 566 passed and 27 skipped with FFmpeg and ffprobe hidden, as on the CI runners. The new tests cover the short-link look-up and fallback, the f2 loader (a stalled load given up on, a late success used by the next download, one load at a time, a load that exits), the network-error classification (f2's own error names, errors wrapped by other errors), the message that replaces the cookie hint and when it must not, and an HTTP client that cannot be built.
- With the real f2 and a local port that drops connection attempts (as a network that swallows packets does), the first load gives up at 15.0 s and the next two calls fail at once; before this change that wait was about 135 s. With the real f2 and yt-dlp behind a proxy that refuses every connection, a full link, a short link and the full link again all say "Could not connect to Douyin" within 3 s, and a YouTube link keeps its own error.
- The packaged engine was built on Linux (Python 3.12, PyInstaller) from the release code and run with no route out, against a local stand-in for the Douyin and ByteDance hosts: it reports 0.7.14; a short link, a Share sentence and a full link download through f2 (the short link is followed once, f2 loads once and in the background); a removed video gives its message; no `./logs` folder appears. With the stand-in's token server dropping connections, the job fails after 17.2 s with the connection message and the engine keeps answering and stops cleanly, where the packaged 0.7.13 engine took 138 s and showed the cookie hint; a second download right after fails in 1.8 s. A load that is slow but ends is used by the next download. With no route at all the connection message shows for a short link, a Share sentence and a user page within 0.3 s and for a full link after about 17 s.
- Review before release: three independent reviewers (the f2 loader and its threads, the control flow of the download, the documents and tests) went through the change and their findings were challenged by skeptics; eight real defects were fixed in #51 before it was merged, each with a test that fails when the fix is taken out. A second round on this release (the notes against the code, the release plumbing, the packaged engine) found no defect that blocks it; it corrected four sentences in these notes and one corner of the code (an HTTP client that cannot be built, for example a SOCKS proxy without its package, now falls back to yt-dlp as it did in 0.7.13).
- Not tried yet: a real Douyin run of this change (the build environment cannot reach Douyin; the f2 download itself was tried on the Mac for 0.7.13), the 15 s wait against a real stalled connection on a user's network, Douyin through f2 on Windows and from the Hetzner server, a real HeyGen clip and real fal pictures and clips, and the in-app update from 0.7.13 to 0.7.14. Known limits: with no route at all a full link takes about 17 s to show the connection message (f2 retries its token request until the 15 s limit); after a failed f2 load a download within the next two minutes still skips f2, even if the connection is back; yt-dlp can add up to 30 s before an error shows, and so can following a short link; a DNS filter that answers `0.0.0.0` for a short link still shows yt-dlp's own error; and if only Douyin's token server (`mssdk.bytedance.com`) is blocked, a yt-dlp cookie failure also reads "Could not connect to Douyin": unblock that host.
- The tag also carries two repository chores (#48, #50: a log hook for cloud sessions under `.claude/`) that the app and the engine do not use. #40 (TikTok inbox) is not in this release.

## Downloads
- macOS Apple Silicon: DMG installer.
- Windows x64: EXE or MSI installer.
- In-app updates use the signed update bundles and latest.json included in this release. The update replaces the engine inside the app only: a remote engine (the Hetzner server, or the Windows PC) has to be updated on its own, by a deploy or by reinstalling its MSI. Until it is, an engine still on 0.7.13 keeps its Douyin behaviour: a short link or Share sentence that f2 cannot read gets no yt-dlp fallback, a first failure takes over two minutes on a stalled network, and the cookie hint shows when there is no connection (an engine older than 0.7.13 has no Douyin download at all). Settings → Engine status shows 0.7.14 once the engine is updated.
